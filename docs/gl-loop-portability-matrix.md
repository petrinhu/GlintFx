# gl-loop-portability-matrix.md

> **Audience: a consumer of this library, deciding whether to trust its GL context handle on Linux and on Windows.** This document is written for that reader, not for this project's own contributors: every row below describes an EFFECT the consumer can observe by calling the public API (`glintfx::gltfx_gl_context`, `include/glintfx/platform/gl/context.hpp`, `gfx_option.hpp`, `gpu.hpp`), never an internal function name, unless that name is itself part of the public contract (`open()`, `is_open()`, `make_current()`, `swap_buffers()`, `proc_address()`, `set_option()`, `option()`, `option_support()`, `gpu()` are; `gl_context_impl`, `gl_context_adapter_port`, anything under `src/` is not).
>
> **This is the entregável of the API review dedicated to `GL-CONTEXT`/`LOOP-RUN`** (`docs/plano-w6b-placa-e-laco.md`, fatia 2b "C-A comum + PMU-GL"). Versioned, the same reasoning `window-portability-matrix.md` (this document's own model, one directory up) already gives for itself.
>
> **The same two house rules `window-portability-matrix.md` holds itself to, unchanged:**
> 1. No sentence here claims equivalence, or divergence, that was not actually measured. Where the two systems have not been proven equal, that is written down as "not yet proven equal," never papered over with a plausible-sounding guess.
> 2. Every sentence that claims something was measured names the exact test that measured it, on the line right after the claim. A sentence with no test named next to it is an opinion, not a measurement, and does not belong in this table.
>
> No volatile digit lives in this document (test counts, line numbers, run numbers): where a fact would need one, this document names the command or the test that produces it instead.

## Scope, and what this fatia can prove today

This fatia (`GL-CONTEXT` 2b) froze the PUBLIC CONTRACT of the context handle and the graphics-option mechanism, and delivered the OS-agnostic pure atoms both platform adapters sit on top of: it did **not**, by itself, deliver either adapter (Wayland/EGL landed as fatia 3, Win32/WGL as fatia 4).

**Both of those have since landed** (`src/platform/wayland/egl_context_adapter.cpp`, `src/platform/win32/wgl_context_adapter.cpp`), exercised for real, through the public API alone, on both systems, by `tests/parity/gl_context_parity_test.cpp`. The rows below that depend on a real, open GL context are therefore **no longer uniformly "not yet implemented"**: each one now states, per platform, exactly what that test asserts equal, what it only measures and prints without asserting, and what nothing exercises yet - never a blanket claim in either direction.

This document grows exactly when `context.hpp`/`gpu.hpp` do, never ahead of them; the same rule `window-portability-matrix.md` already commits to for its own scope.

## The matrix

| Effect a consumer observes | Linux (Wayland/EGL) | Windows (Win32/WGL) | Status |
|---|---|---|---|
| Opening a context with an unknown option id, an out-of-range value, a `read_only` entry, a repeated id, a null `options` pointer with a positive count, or `gpu_preference` requested as anything but `no_preference` | Refused before any adapter is ever asked, naming the option in `rejected_value()`. | Refused the same way, before `wglCreateContextAttribsARB` is ever reached. | **Proven identical, by construction**: one shared validation atom (`gl_context_desc_validation.hpp`) runs before either backend is ever consulted, never a per-backend check that could drift. Proven by: `gl_context_desc_validation_test` (five cases: an empty list; `vsync=on`; `gpu_preference=prefer_dedicated` refused; a repeated id refused; a null pointer with a positive count refused). |
| A second `gltfx_gl_context::open()` on the SAME window, asking for a different `open_only` option than the first context fixed | Refused with `invalid_argument`, naming the option, before the adapter is asked whether it even supports it. | Refused the identical way: the fixation atom runs first regardless of which system's driver would otherwise have accepted the second value (EGL) or refused it for an unrelated reason (`SetPixelFormat` may only run once per `HWND`). | **Proven identical, by construction** (D-W6b-25): `gfx_open_only_fixation.hpp`'s own `resolve_gfx_open_only_fixation()` decides this from plain data, with no adapter in the picture: the SAME decision on every system, never "Wayland happens to allow it, Windows happens to refuse it." Proven by: `gfx_open_only_fixation_test` (the closed six-cell enumeration `{nada fixado, igual, diferente} x {pedida, omitida}`). |
| The GL version/profile a driver hands back after context creation | 3.3 core or newer, core profile bit set, is the only shape this library accepts: anything else (a compatibility profile, a version below 3.3, no profile bit at all) is refused with `platform_failure`, `rejected_value() == "gl_version"`. | The identical rule, over the same two GL queries (`GL_MAJOR_VERSION`/`GL_MINOR_VERSION`/`GL_CONTEXT_PROFILE_MASK`), regardless of which extension path (EGL vs. WGL) obtained the context. | **The RULE is proven identical, by construction** (`gl_version_policy.hpp` is one pure atom, no `#if` in it, shared by both adapters): proven by `gl_version_policy_test` (seven named cases plus the closed 12-cell enumeration `{major<3, ==3&minor<3, ==3&minor>=3, >3} x {core, compat, none}`). **What a REAL driver on either platform actually negotiates for a 3.3 request is now proven too, live, not only by construction**: `gl_context_parity_test` opens a real context on each system and fails the run outright the moment a driver hands back anything short of the 3.3-core floor - the identical expectation enforced independently on each system, proven by: `gl_context_parity_test`. The exact `major`/`minor` numbers a real driver reports are measured and printed (`MEASURED gl_context_parity_test.gl_major`/`.gl_minor`) but never asserted equal to each other - only that both clear the 3.3-core floor is. |
| The GPU kind (`unknown`/`software`/`shared`/`dedicated`) a freshly-constructed context reports before any adapter has told it anything | `unknown`, never a guess. | `unknown`, for the identical reason. | **Proven identical, by construction**: `gpu_kind_state.hpp` is the ONE shared atom both adapters are expected to embed: a context is born not knowing, and stays that way until something real tells it otherwise (D-W6b-13: "unknown significa 'o sistema nao disse', nunca 'provavelmente integrada'"). Proven by: `gpu_kind_state_test` (born unknown with an empty name; learns exactly what it is told; never fabricates a name; the closed four-value enumeration). **What a REAL driver reports on either platform is not yet measured**; that is fatia 5b's own classification atoms (`drm_gpu_kind`, `dxgi_gpu_kind`), not this fatia. |
| Whether the EGL/GL surface needs resizing before the next frame, when the window's own `pixel_size()` changes (HiDPI, `fractional-scale`) | The surface is resized to the window's own current `pixel_size()` whenever it differs from what the surface was last resized to; refuses a zero-pixel size outright, the same case `gltfx_window::open()` already refuses upstream, so this policy never actually has to handle it in production. | Nothing to decide: the device context already follows the `HWND`'s own client area, no separate resize step exists on this platform (D-W6b-5). | **The Linux-side POLICY is proven, by construction, with SYNTHETIC scale-2 values** (window-portability-matrix.md's own "memoria da casa: o servidor nunca reporta escala != 1" applies here too): proven by `gl_surface_size_policy_test` (matching sizes do not resize; a synthetic scale-2 doubling resizes; returning to scale 1 shrinks back; a zero-pixel size is refused, never silently accepted). **Whether the real `wl_egl_window_resize()` call this policy feeds actually keeps a live surface correct is not yet measured**; that is fatia 3's own job. |
| Opening a context, making it current, presenting a frame, resolving a GL function address, reading back the GPU actually in use | **Implemented**: `platform::selected_gl_context_adapter` resolves to `src/platform/wayland/egl_context_adapter.cpp`, a real EGL context opened over the window, backing `make_current()`/`swap_buffers()`/`proc_address()` for real (fatia 3). | **Implemented**: the same type resolves to `src/platform/win32/wgl_context_adapter.cpp`, doing the identical job over WGL (fatia 4). | **Opening, making current, presenting a frame and resolving a GL function address are proven identical, live, not by construction**: `gl_context_parity_test` runs the exact public-API sequence a consumer would (`gltfx_display`/`gltfx_window`/`gltfx_gl_context` only, never a concrete adapter type directly) on both systems, and fails the run outright the moment proc-address resolution, the GL >= 3.3 core check, a pixel readback after a real draw, the first-presented timing budget, or the vsync-off timing budget disagrees with what it expects - the identical expectation enforced independently on each system, which is what makes agreement between the two a consequence of the run passing at all, never a separate cross-platform diff step. The two context-reopen (fixation) cases from the row above are exercised the same way, against a real adapter this time, not only the shared validation atom. Proven by: `gl_context_parity_test`, and `gl_context_adapter_port_concept_test`'s compile-time contract both adapters are checked against (a positive control, `fake_gl_context_adapter`, and a negative control missing exactly `gpu()`). **Reading back the GPU actually in use is measured and printed on both systems (`MEASURED gl_context_parity_test.gpu_kind_raw`/`.gpu_name_hash` and its per-entry siblings), but deliberately NOT asserted equal yet**: only that at least one GPU entry is ever reported (`gpu_enumeration_count >= 1`, GODS_LAWS.md L-40's own non-empty floor) is asserted; the stronger claim (`gpu().kind` itself agreeing across systems) is left for after a first real run's numbers have actually been seen, per this test's own committed reasoning, never guessed at beforehand. The GL major/minor version, the renderer name, the vsync-on frame-time average, and whether adaptive vsync is supported are measured and printed the same way, also never asserted equal: a real driver's own numbers are allowed to differ between the two systems. |
| `set_option()`/`option()`/`option_support()` on a live context | **Implemented**, over the real adapter above. | **Implemented**, for the identical reason. | **`set_option()` and `option_support()` are exercised for real, on both systems, by `gl_context_parity_test`** - not only the FACADE logic in isolation. `option_support()`'s own sweep over every registry row is asserted non-empty on both systems (GODS_LAWS.md L-40's own piso), and three of its rows carry a cross-platform-asserted answer: `auto_choice_reason` and `power_source` must report `read_only_here`, and `vsync` must report `supported` - the identical expectation enforced independently on each system. `set_option(vsync=off)`, `set_option(vsync=on)` and `set_option(vsync=adaptive)` (allowed to be refused, since not every driver supports adaptive vsync) are all exercised, and the resulting off/on/off/on toggle sequence is required to keep presenting successfully throughout. Proven by: `gl_context_parity_test`. **`option()` itself - reading back a value already applied - is not called by that test on either system**: it is wired into the facade and compiles against both real adapters (`gl_context_facade.cpp`, `src/platform/gl/CMakeLists.txt`), but nothing in this project's own test suite yet reads a live value back through it; that remains not yet proven, honestly, rather than assumed to work because the rest of the facade does. **`msaa_samples` and `srgb_framebuffer` support are measured and printed (`MEASURED gl_context_parity_test.msaa_support`/`.srgb_support`) but never asserted equal**: whether a real driver happens to support multisampling or an sRGB-capable default framebuffer is allowed to differ between the two systems. |
| Setting `preset` to `automatic` (or to any other named preset), reading `auto_choice_reason`, or reading `power_source` via `set_option()`/`option()` | **Accepted, not refused - and currently a no-op.** `option_support(preset)` reports `supported` (the row above), and `set_option(preset=...)` returns success: the value is stored and can be read back through `option()`. Nothing downstream ever resolves `automatic` into a concrete, named preset, and setting any preset - `automatic` included - never changes any OTHER option's own value (`vsync`, `frame_rate_cap`, `msaa_samples`, ...): `auto_choice_reason` stays whatever it was born as, never populated with a real reason. | The identical no-op, for the identical reason: the same shared facade code path both platforms call into. | **Deliberately silent about doing nothing, until this row existed to say so.** The mechanism this row describes - `gfx_preset_table`, `auto_preset_rule`, and the two platform `power_source_adapter`s that would read whether the machine is on battery or mains power - was never built; it is tracked as its own item, `GFX-PRESET`, out of this wave's scope by the líder's own decision (08/09/2026), not a silent gap. `wayland_egl_context_adapter::apply_option()`'s own header comment names this directly: "every other `live` id (frame_rate_cap, preset) is accepted here with no adapter-side effect yet." No test asserts anything about this row - there is nothing working yet to prove, only a present, silent behavior to declare so a consumer does not have to discover it by reading source. |

## The loop's own matrix (LOOP-RUN, fatia 6b, `docs/plano-w6b-fatias-6-8.md` sec. 8.3)

**Audience note, unchanged from the paragraph at the top of this document:** every row below describes an effect a consumer can observe through `glintfx::gltfx_loop` (`include/glintfx/platform/loop/loop.hpp`) or `glintfx::gltfx_fixed_step` (`include/glintfx/core/fixed_step.hpp`), never an internal name (`loop_impl`, `frame_cap_schedule`, `compute_frame_tick`, `allocate_loop_impl` are not part of the public contract).

**What this fatia landed, and what it deliberately did not:** fatia 6a shipped the frozen public surface (`gltfx_frame_tick`, `gltfx_loop_callbacks`, `gltfx_fixed_step`) and three OS-agnostic pure atoms it sits on (`frame_tick_state.hpp`, `frame_cap_schedule.hpp`, `loop_callbacks_validation.hpp`); fatia 7 gave both display adapters `wait_events()` and both GL-context adapters `present_would_skip()`. This fatia (6b) is the facade that PIMPLs `gltfx_loop` over all of that - `open()`/`is_open()`/`step()`/`present()`/`run()` in `src/platform/loop/loop_facade.cpp`. **D-W6b-56 is a decision of SCOPE, not an oversight this document is hiding: the facade itself carries no dedicated unit test.** Every row below that names a fact about `step()`/`present()`/`run()`'s own wiring is therefore honestly marked "compiles and is wired to the atom below it; not yet exercised against a real display, window or GL context" - the row on `open()`'s own allocation-failure path is the one exception, because that ONE call is provably reachable without touching the operating system (`loop_open_alloc_failure_test.cpp`'s own header comment explains why). The rows this document expects to change from "not yet exercised" to "proven, live" are the ones fatia 8's own `loop_parity_test`/`loop_hidden_test` (`docs/plano-w6b-fatias-6-8.md` sec. 8.4) will add - this document is rewritten again then, never before.

| Promise (`loop.hpp`'s own P1..P10) | Linux (Wayland) | Windows (Win32) | Status |
|---|---|---|---|
| P1. `step()`/`present()` never block indefinitely, exceptions declared and counted | The loop's own only wait site is the frame-rate-cap spin (`wait_for_frame_cap()`'s tight loop on `clock.now()`, `src/platform/loop/loop_engine.hpp` since the LOOP-RUN cobertura S2 extraction) - a real, finite budget of at most one period, never a sleep. | Identical: the same engine code, no `#if` in it. | **The loop introduces no NEW unbounded wait, proven by construction of the manifest, not by running the loop**: `tests/wait_points.txt`/`check_wait_points.py` (`GODS_LAWS.md` L-36/L-40) enumerate every site in `loop_engine.hpp`/`steady_loop_clock.hpp`/`loop_facade.cpp` that reads a clock or could block, counted by the gate, never here - all sites are `nao-espera` (a plain clock read) or `teto-nosso` (the bounded spin), zero `sem-teto-nao-declarado`. Proven by: `check_wait_points_test`, `check_wait_points_selftest`. The exceptions this promise inherits from the display/context adapters underneath (vsync-on `present()` waiting one refresh period on Windows; a driver refusing `eglSwapInterval(0)` on Linux) are documented at their own sites, not repeated here - `present()` simply forwards whatever `swap_buffers()` returns. |
| P2. `frame_index` starts at 1, +1 per `step()`, no gap, independent of `should_render` | The FORMULA is proven. | Identical formula, same atom, no `#if`. | **Proven by construction, for the atom**: `compute_frame_tick()` (`frame_tick_state.hpp`) always returns `previous_frame_index + 1`, unconditionally. Proven by: `frame_tick_state_test`. **Whether `gltfx_loop::step()` itself feeds this atom the right `previous_frame_index` across real calls is not yet exercised** - awaits `loop_parity_test` (fatia 8). |
| P3. Order inside `step()`/`run()` | `step()`'s own five numbered actions (pump, read `close_requested()`, wait-if-hidden, wait-for-cap, read the clock) run in exactly that order, unconditionally, by construction of `loop_facade.cpp` (`GODS_LAWS.md` L-17: each is its own function, `step()` itself only sequences them). `run()`'s own order (`step()` -> `on_frame` -> if `should_render`: `on_render` -> `present()`) is the same, one straight-line function, no branch that could reorder it. | Identical: no `#if` anywhere in `loop_facade.cpp`. | **Proven by construction of the source, not yet exercised live**: there is no test today (by design, D-W6b-56) that opens a real display/window/context and observes the order a consumer would actually see - `loop_parity_test`'s own `set_title()`-then-read-it-back case (fatia 8) is what turns this into a measurement. |
| P4. `should_render`'s two implications, including recovery | The FORMULA (`(last_present != skipped_hidden) \|\| probe_says_visible`) is proven, including the recovery cell an earlier draft of this plan got wrong (`docs/plano-w6b-fatias-6-8.md` finding F4). | Identical formula, same atom. | **Proven by construction, for the atom**: `frame_tick_state_test`'s own 2x2 enumeration ({`presented`, `skipped_hidden`} x {probe visible, probe hidden}), all four cells, contagem impressa. **Whether `step()` feeds this atom a real `present_would_skip()` reading is not yet exercised** - awaits `loop_hidden_test` (fatia 8). |
| P5. `elapsed`: monotonic, never negative, clamped to `k_gltfx_max_frame_elapsed`, zero on the first tick | The clamp and the "clock stepped backward gives zero" rule are proven for the atom; `gltfx_now()` itself is proven monotonic and advancing. | Identical atom and clock contract. | **Proven by construction**: `frame_tick_state_test` (a 3-second gap clamps to the constant, read from `k_gltfx_max_frame_elapsed` itself, never a copied literal; a backward clock gives zero; the first tick gives zero). `time_test`'s own `now_advances_and_never_runs_backwards` proves `gltfx_now()` (100 consecutive pairs, plus a loop bounded at 10^7 iterations until it changes). **The REAL cadence a live loop produces is not yet measured** - `loop_parity_test`'s own `mean_step_ns`/`max_step_ns` (fatia 8). |
| P6. The loop never simulates; `gltfx_fixed_step` is the opt-in atom for physics/game rules | `gltfx_fixed_step_accumulate()` proven: the spiral is capped by `max_steps` without ever growing `accumulated`; `dt <= 0` is a total no-op; `alpha` stays in `[0,1)`. | Identical atom, no platform code at all. | **Proven by construction**: `fixed_step_test`'s own closed enumeration ({below, equal, multiple, overflow} x {capped, uncapped} = 8 cells, contagem impressa). This is the one promise this fatia proves completely, live: the atom is the whole promise, and no facade wiring sits between a consumer and it - `gltfx_loop` itself never calls it (P6's own point). |
| P7. `frame_rate_cap` honored by deadline, no drift, live changes take effect next tick, coexists with vsync | The scheduling ALGORITHM is proven, including the anti-drift property (deadline advances from the previous deadline, never from a freshly measured `now`) and both safety valves (reanchor when more than one period late; never wait past one period on a backward clock). | Identical atom. | **Proven by construction, for the atom**: `frame_cap_schedule_test`'s own six cases, including the "sem deriva" one (300 consecutive 60 Hz periods sum to 5 s +/- 1 ms - the case that kills the `deadline = now + period` mutant `docs/plano-w6b-fatias-6-8.md` sec. 8.4 names). **Whether `step()` reads `frame_rate_cap` correctly and drives `wait_for_frame_cap()` with it is not yet exercised** - awaits `loop_parity_test`'s own 30-frame, `cap=30 Hz` timing window (fatia 8). |
| P8. A hidden window never draws, never spins the CPU | The SONDA (`present_would_skip()`) each adapter answers is proven by that adapter's own tests (`egl_context_adapter`/`wgl_context_adapter`, a prior fatia), not repeated here. | Same. | **Whether `gltfx_loop` itself wires the sonda into `should_render`, skips `on_render`, and actually sleeps between ticks (`wait_while_hidden()`) is not yet exercised** - by design (D-W6b-56): this is exactly what `loop_hidden_test` (fatia 8) exists to measure (`cpu_ns`/`wall_ns`/`rendered_while_hidden`, per `docs/plano-w6b-fatias-6-8.md` sec. 6.1). |

| P10. `display`/`window`/`context` must outlive the loop; `open()` refuses by name whichever is not open | `open()`'s own three `is_open()` checks (`display`, `window`, `context`, in that order) are written, matching the same precondition shape `gltfx_window::open()`/`gltfx_gl_context::open()` already use one layer down. | Identical, no platform code in `open()` itself. | **Not yet exercised by any test, honestly declared rather than assumed**: no test today opens three real handles and calls `gltfx_loop::open()` with one of them deliberately closed - that needs a real display (`GODS_LAWS.md` L-09: container-only), and D-W6b-56 leaves ALL live exercise of the facade to fatia 8. **What IS proven, and is the only slice of `open()` a test can reach without a real display**: the allocation `open()` performs for its own opaque impl degrades to `gltfx_err_code::out_of_memory`, never `std::terminate()`, when the heap refuses it - proven by `loop_open_alloc_failure_test` (`allocate_loop_impl()`, the same "pure enough to test directly" shape `gfx_open_only_fixation_test` already established one fatia over for the identical class of allocation). |

## What this document does not cover

Choosing a GPU (`gpu_preference` stays `no_preference`-only until `GL-GPU-PREFERENCE`), enumerating several GPUs on demand (`gltfx_gpu_enumeration`, fatia 5b), a graphics-preset table and automatic choice (fatia 5c), input delivery (`INPUT-EVENTS`, W7 - `gltfx_loop_callbacks::on_event` stays refused-if-filled until then), and anything else `docs/plano-w6b-fatias-6-8.md` itself marks as belonging to a later fatia or wave (sec. 10's own pendency list) are out of scope here by construction: this matrix only ever describes the surface `include/glintfx/platform/gl/{context,gpu}.hpp` and `include/glintfx/platform/loop/loop.hpp`/`include/glintfx/core/fixed_step.hpp` freeze today, and grows exactly when those headers do, never ahead of them.

## How this document stays honest

Every row above is either "proven identical, by construction or by a named test," or "not yet proven, honestly declared as depending on a fatia not yet landed." Neither state is final: fatia 3 (Wayland/EGL) and fatia 4 (Win32/WGL) are what turned the GL-context "not yet implemented" rows into either a proof (citing `gl_context_parity_test`) or a declared, permanent divergence, and fatia 8 (`loop_parity_test`/`loop_hidden_test`) is what will do the identical thing to every LOOP-RUN row above still marked "not yet exercised" - never silently, and never by a contributor's own guess.
