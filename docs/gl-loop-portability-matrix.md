# gl-loop-portability-matrix.md

> **Audience: a consumer of this library, deciding whether to trust its GL context handle on Linux and on Windows.** This document is written for that reader, not for this project's own contributors: every row below describes an EFFECT the consumer can observe by calling the public API (`glintfx::gltfx_gl_context`, `include/glintfx/platform/gl/context.hpp`, `gfx_option.hpp`, `gpu.hpp`), never an internal function name, unless that name is itself part of the public contract (`open()`, `is_open()`, `make_current()`, `swap_buffers()`, `proc_address()`, `set_option()`, `option()`, `option_support()`, `gpu()` are; `gl_context_impl`, `gl_context_adapter_port`, anything under `src/` is not).
>
> **This is the entregável of the API review dedicated to `GL-CONTEXT`/`LOOP-RUN`** (`docs/plano-w6b-placa-e-laco.md`, fatia 2b "C-A comum + PMU-GL"). Versioned, the same reasoning `window-portability-matrix.md` (this document's own model, one directory up) already gives for itself.
>
> **The same two house rules `window-portability-matrix.md` holds itself to, unchanged:**
> 1. No sentence here claims equivalence, or divergence, that was not actually measured. Where the two systems have not been proven equal, that is written down as "not yet proven equal," never papered over with a plausible-sounding guess.
> 2. Every sentence that claims something was measured names the exact test that measured it, on the line right after the claim. A sentence with no test named next to it is an opinion, not a measurement, and does not belong in this table.
>
> No volatile digit lives in this document (test counts, line numbers, run numbers): where a fact would need one, this document names the command or the test that produces it instead.

## Scope, and what this fatia can prove today

This fatia (`GL-CONTEXT` 2b) freezes the PUBLIC CONTRACT of the context handle and the graphics-option mechanism, and delivers the OS-agnostic pure atoms both platform adapters will sit on top of — it does **not** deliver either adapter (Wayland/EGL is fatia 3, Win32/WGL is fatia 4). Every row below that depends on a real, open GL context is therefore marked **not yet implemented**, honestly, rather than guessed at: the rows that ARE fillable today are the ones a pure atom, tested without any operating-system call, already proves identical by construction.

This document grows exactly when `context.hpp`/`gpu.hpp` do, never ahead of them — the same rule `window-portability-matrix.md` already commits to for its own scope.

## The matrix

| Effect a consumer observes | Linux (Wayland/EGL) | Windows (Win32/WGL) | Status |
|---|---|---|---|
| Opening a context with an unknown option id, an out-of-range value, a `read_only` entry, a repeated id, a null `options` pointer with a positive count, or `gpu_preference` requested as anything but `no_preference` | Refused before any adapter is ever asked, naming the option in `rejected_value()`. | Refused the same way, before `wglCreateContextAttribsARB` is ever reached. | **Proven identical, by construction**: one shared validation atom (`gl_context_desc_validation.hpp`) runs before either backend is ever consulted, never a per-backend check that could drift. Proven by: `gl_context_desc_validation_test` (five cases: an empty list; `vsync=on`; `gpu_preference=prefer_dedicated` refused; a repeated id refused; a null pointer with a positive count refused). |
| A second `gltfx_gl_context::open()` on the SAME window, asking for a different `open_only` option than the first context fixed | Refused with `invalid_argument`, naming the option, before the adapter is asked whether it even supports it. | Refused the identical way — the fixation atom runs first regardless of which system's driver would otherwise have accepted the second value (EGL) or refused it for an unrelated reason (`SetPixelFormat` may only run once per `HWND`). | **Proven identical, by construction** (D-W6b-25): `gfx_open_only_fixation.hpp`'s own `resolve_gfx_open_only_fixation()` decides this from plain data, with no adapter in the picture — the SAME decision on every system, never "Wayland happens to allow it, Windows happens to refuse it." Proven by: `gfx_open_only_fixation_test` (the closed six-cell enumeration `{nada fixado, igual, diferente} x {pedida, omitida}`). |
| The GL version/profile a driver hands back after context creation | 3.3 core or newer, core profile bit set, is the only shape this library accepts — anything else (a compatibility profile, a version below 3.3, no profile bit at all) is refused with `platform_failure`, `rejected_value() == "gl_version"`. | The identical rule, over the same two GL queries (`GL_MAJOR_VERSION`/`GL_MINOR_VERSION`/`GL_CONTEXT_PROFILE_MASK`), regardless of which extension path (EGL vs. WGL) obtained the context. | **The RULE is proven identical, by construction** (`gl_version_policy.hpp` is one pure atom, no `#if` in it, shared by both adapters): proven by `gl_version_policy_test` (seven named cases plus the closed 12-cell enumeration `{major<3, ==3&minor<3, ==3&minor>=3, >3} x {core, compat, none}`). **What a REAL driver on either platform actually negotiates for a 3.3 request is not yet measured** — that is fatia 3/4's own `gl_context_parity_test` (container/`ctest`), not this fatia. |
| The GPU kind (`unknown`/`software`/`shared`/`dedicated`) a freshly-constructed context reports before any adapter has told it anything | `unknown`, never a guess. | `unknown`, for the identical reason. | **Proven identical, by construction**: `gpu_kind_state.hpp` is the ONE shared atom both adapters are expected to embed — a context is born not knowing, and stays that way until something real tells it otherwise (D-W6b-13: "unknown significa 'o sistema nao disse', nunca 'provavelmente integrada'"). Proven by: `gpu_kind_state_test` (born unknown with an empty name; learns exactly what it is told; never fabricates a name; the closed four-value enumeration). **What a REAL driver reports on either platform is not yet measured** — that is fatia 5b's own classification atoms (`drm_gpu_kind`, `dxgi_gpu_kind`), not this fatia. |
| Whether the EGL/GL surface needs resizing before the next frame, when the window's own `pixel_size()` changes (HiDPI, `fractional-scale`) | The surface is resized to the window's own current `pixel_size()` whenever it differs from what the surface was last resized to — refuses a zero-pixel size outright, the same case `gltfx_window::open()` already refuses upstream, so this policy never actually has to handle it in production. | Nothing to decide: the device context already follows the `HWND`'s own client area, no separate resize step exists on this platform (D-W6b-5). | **The Linux-side POLICY is proven, by construction, with SYNTHETIC scale-2 values** (window-portability-matrix.md's own "memoria da casa: o servidor nunca reporta escala != 1" applies here too): proven by `gl_surface_size_policy_test` (matching sizes do not resize; a synthetic scale-2 doubling resizes; returning to scale 1 shrinks back; a zero-pixel size is refused, never silently accepted). **Whether the real `wl_egl_window_resize()` call this policy feeds actually keeps a live surface correct is not yet measured** — that is fatia 3's own job. |
| Opening a context, making it current, presenting a frame, resolving a GL function address, reading back the GPU actually in use | Not yet implemented — `platform::selected_gl_context_adapter` does not exist on this platform yet (fatia 3, Wayland/EGL). | Not yet implemented — the same type does not exist on this platform yet either (fatia 4, Win32/WGL). | **Not yet proven, and not yet implementable**: `gltfx_gl_context::open()`'s own facade (`gl_context_facade.cpp`) is written and reviewed as part of this fatia, but is deliberately NOT wired into `glintfx_library`'s own build (`src/platform/gl/CMakeLists.txt`'s own header comment) until whichever of fatia 3/4 lands provides the adapter type it PIMPLs over. The compile-time CONTRACT both adapters will be checked against already exists and is provably satisfiable: `gl_context_adapter_port_concept_test` (a positive control, `fake_gl_context_adapter`, and a negative control missing exactly `gpu()`). |
| `set_option()`/`option()`/`option_support()` on a live context | Not yet implemented (depends on a real adapter, see the row above). | Not yet implemented, for the identical reason. | **Not yet proven.** The FACADE logic that will forward these calls (validate, check `option_support()`, apply, then read back) is written in `gl_context_facade.cpp`, but exercising it needs the same adapter fatias 3/4 provide — this is `P-GL`'s own scope (`docs/plano-w6b-placa-e-laco.md` fatia 5), not this one. |

## What this document does not cover

Choosing a GPU (`gpu_preference` stays `no_preference`-only until `GL-GPU-PREFERENCE`), enumerating several GPUs on demand (`gltfx_gpu_enumeration`, fatia 5b), a graphics-preset table and automatic choice (fatia 5c), the main loop and fixed-step accumulator (fatia 6), input delivery, and anything else `docs/plano-w6b-placa-e-laco.md` itself marks as belonging to a later fatia or wave are out of scope here by construction — this matrix only ever describes the surface `include/glintfx/platform/gl/{context,gpu}.hpp` freezes today, and grows exactly when that header does, never ahead of it.

## How this document stays honest

Every row above is either "proven identical, by construction or by a named test," or "not yet proven, honestly declared as depending on a fatia not yet landed." Neither state is final: fatia 3 (Wayland/EGL) and fatia 4 (Win32/WGL) are what turn the "not yet implemented" rows into either a proof (this document rewritten, citing `gl_context_parity_test`) or a declared, permanent divergence — never silently, and never by a contributor's own guess.
