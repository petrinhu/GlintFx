# Uma linha aqui declara que uma funcao noexcept, achada pela regua
# como alocando (direta ou transitivamente) sem `try` eficaz, NAO
# reprova o portao - e POR QUE isso e aceitavel, nunca uma forma de
# calar o portao. Formato, um registro por linha, cinco campos
# separados por "|" (comentarios com "#", linhas em branco ignoradas):
#
#   caminho | funcao | tipo | razao | item
#
# - caminho: caminho relativo do arquivo (raiz do repositorio) onde a
#   funcao noexcept esta declarada.
# - funcao: nome exato da funcao, como a regua o extrai (sem
#   qualificador de classe/namespace, sem numero de linha - numero de
#   linha apodrece a cada edicao).
# - tipo: EXATAMENTE um dos dois valores abaixo, nunca outro:
#     * FALSO-POSITIVO-DA-REGUA - afirmacao sobre a FERRAMENTA: a forma
#       nao aloca de verdade (ex.: uma classe de construcao que a
#       calibracao ainda nao cobre). O orquestrador pode decidir, com
#       razao escrita e, quando fizer sentido, uma fixture nova no
#       mesmo commit que prove a classe.
#     * DECISAO-LIDER:DD/MM/AAAA - afirmacao sobre o PRODUTO: aqui a
#       biblioteca aceita alocar dentro de `noexcept`, por decisao
#       explicita do lider naquela data. Excecao a uma ordem dele - SO
#       ele abre uma linha deste tipo (GODS_LAWS.md L-01/L-10).
# - razao: texto livre explicando o motivo, nunca vazio.
# - item: o ID do item em TODO.md que rastreia a morte desta linha, ou
#   o sentinela SEM-PENDENCIA quando a razao e permanente. Item
#   marcado CONCLUIDO em TODO.md com a linha ainda viva REPROVA (mesma
#   regra de morte de tests/parity_exceptions.txt,
#   check_test_parity.py's own validate_exceptions()).
