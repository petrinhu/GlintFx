# window-portability-matrix.md

> **Audience: a consumer of this library, deciding whether to trust its window handle on Linux and on Windows.** This document is written for that reader, not for this project's own contributors: every row below describes an EFFECT the consumer can observe by calling the public API (`glintfx::gltfx_display`, `glintfx::gltfx_window`, `include/glintfx/platform/window/{display,window}.hpp`), never an internal function name, unless that name is itself part of the public contract (`open()`, `logical_size()`, `pixel_size()`, `state()`, `close_requested()`, `set_title()` are; `handle_message()`, `window_impl`, anything under `src/` is not).
>
> **This is the entregável of the API review dedicated to WL-WINDOW/WIN-WINDOW** (`docs/plano-w6a-janela.md`, fatia 6 "W-D'"). Versioned, because a matrix that only lives in a chat log or a `/var/tmp` note rots faster than one that ships with the source.
>
> **Two house rules this document holds itself to, both new as of this same wave:**
> 1. No sentence here claims equivalence, or divergence, that was not actually measured. Where the two systems have not been proven equal, that is written down as "not yet proven equal," never papered over with a plausible-sounding guess.
> 2. Every sentence that claims something was measured names the exact test that measured it, on the line right after the claim. A sentence with no test named next to it is an opinion, not a measurement, and does not belong in this table.
>
> No volatile digit lives in this document (test counts, line numbers, run numbers): where a fact would need one, this document names the command or the test that produces it instead, the same convention `README.md`'s own "test suite" section already uses.

## Scope

Everything a consumer can call on an open `gltfx_display` or `gltfx_window`: `is_open()`, `pump_events()`, `open()`'s own refusal behavior, `logical_size()`, `pixel_size()`, `state(bit)`, `close_requested()`, `set_title()`. Nothing about a future graphics context or input delivery (`W6b`, not this wave) is in scope here.

## The matrix

| Effect a consumer observes | Linux (Wayland) | Windows (Win32) | Status |
|---|---|---|---|
| Opening a window with a zero width or a zero height | Refused before the compositor ever sees the request, with an error naming the `logical_size` field. | Refused the same way, before `CreateWindowExW` is ever called. | **Proven identical**, by construction: one shared validation layer runs before either backend sees the request, never a per-backend check that could drift. Proven by: `window_desc_validation_test` (`both_dimensions_zero_is_rejected`, `zero_width_only_is_rejected`, `zero_height_only_is_rejected`, `both_dimensions_nonzero_is_accepted`) and `window_parity_test`'s own refusal case, run against both systems. |
| `logical_size()` read the instant `open()` returns successfully | The size the caller requested, in the window system's own coordinate space: by the Wayland protocol's own rule, a client's requested size stands until the compositor's first configure event says otherwise, and `open()` has already waited for that configure before returning. | The window's real client-area size, read synchronously from the operating system the instant the window exists, never a copy of the caller's request. | **Proven identical** (this wave's own fix: an earlier revision reported the caller's raw request on Windows without ever reading it back from the system, which happened to look identical to this row only because nobody had yet asked the two systems to disagree). Proven by: `window_parity_test`, which requires this value to equal the exact size requested, on both systems, through the public API alone. Windows' own read is [`GetClientRect`](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-getclientrect) ("Retrieves the coordinates of a window's client area"), called once, before `open()` returns. |
| `pixel_size()` read the instant `open()` returns successfully | `logical_size()` scaled by the compositor's own announced buffer scale, `1` until the compositor announces otherwise. | `logical_size()` scaled by the window's own DPI at creation, read via [`GetDpiForWindow`](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-getdpiforwindow) ("Returns the dots per inch (dpi) value for the specified window"), base value `96`. | **Not yet proven equal on a display where the two factors actually differ.** Every executor in this project's own CI reports a buffer scale and a DPI that both resolve to the neutral factor, so the two numbers come out equal today regardless of which formula either backend used, including a wrong one. Measured (never asserted equal across systems) by: `window_parity_test`'s own `MEASURED window_parity_test.pixel_width_after_open`/`pixel_height_after_open` lines, read by the `parity` job's own measured-value comparison. A HiDPI Windows display or a fractional-scale Wayland compositor is what would finally exercise the divergent case; neither exists in this project's own CI fleet today. |
| `state(active)` / `state(maximized)` / `state(fullscreen)` read the instant `open()` returns successfully | Reflects only what the compositor has already announced by that point: a window this library never maps or shows may or may not have been announced as active, depending on the compositor's own policy for an unmapped toplevel. | Reflects only what the operating system has already sent by that point: this library never calls `ShowWindow` on the window it creates, and whether an unshown window ever receives `WM_ACTIVATE` on a given Windows version is exactly the open question this row exists to measure, not an assumed fact. | **Still measuring, not yet compared.** Neither side promises a value here today; the two systems are not required to agree on `active` before the caller's first `pump_events()` call. Measured (never asserted) by: `window_parity_test`'s own `MEASURED window_parity_test.active_after_open`/`maximized_after_open`/`fullscreen_after_open` lines, read by the `parity` job's own measured-value comparison, the table that will eventually turn this row into either a promise or a declared, permanent divergence. |
| `close_requested()` read the instant `open()` returns successfully | Always false: a freshly opened window has not yet been asked to close by anything. | Always false, for the identical reason. | **Proven identical**, by construction (both backends start a brand-new state object with no close signal latched, and nothing in `open()` itself can raise one). Proven by: `window_parity_test`. |
| Calling `set_title()` after `open()`, with a title containing accented UTF-8 text | Succeeds; the compositor's title bar (if the window manager renders one) shows the new text. | Succeeds; the window's own title bar shows the new text, via [`SetWindowTextW`](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setwindowtextw) ("Changes the text of the specified window's title bar"). | **Proven identical.** Proven by: `window_parity_test`, which calls `set_title()` with accented text after opening and requires success on both systems. |
| Calling `set_title()` (or opening a window) with a title containing an embedded NUL byte or invalid UTF-8 | Refused, naming the field, before either backend's own system call ever runs. | Refused the same way. | **Proven identical at the shared validation layer both backends call before touching the system** (never a per-backend check that could drift). Proven by: `window_desc_validation_test` (`embedded_nul_byte_is_rejected`, `invalid_utf8_is_rejected`). Not yet exercised through a real, end-to-end `open()`/`set_title()` call against either live system with this exact malformed input: `window_parity_test` only ever sends a valid, accented title through the public API. |
| Destroying a `gltfx_window` and its `gltfx_display` at the end of a scope, with no explicit `close()` call | The window is torn down before the display, in reverse of the order they were opened, the reverse-of-creation teardown this handle's own contract requires. | The window is torn down before the display, for the identical reason. | **Proven identical**, by construction (C++ destructor order for locals is always reverse-of-declaration, and both handles are RAII types with no behavior beyond that). Proven by: `window_parity_test`'s own scope end, which IS the demonstration (its own header comment: "this scope's own end is the live demonstration, not a separate assertion this file could make after the fact"). |

## What this document does not cover

A graphics context, input event delivery, cursor/gamepad/audio, and anything else `docs/plano-w6a-janela.md` itself marks as belonging to a later wave (`W6b` and beyond) are out of scope here by construction: this matrix only ever describes the surface `include/glintfx/platform/window/{display,window}.hpp` freezes today, and grows exactly when that header does, never ahead of it.

## How this document stays honest

Every row above is either "proven identical, by construction or by a named test," or "not yet proven, measured without an assertion of equality, by a named test." Neither state is final: the `parity` job's own measured-value comparison (its own `check_measured_parity.py`) is what turns a "not yet proven" row into either a promise (the row above gets rewritten as "proven identical," and the parity table stops carrying that key at all) or a declared, permanent divergence, never silently, and never by a contributor's own guess.
