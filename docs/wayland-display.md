# wayland-display.md

> **Internal engineering document, not a public API reference.** Everything described here lives under `src/platform/wayland/` - no header under `include/glintfx/`, no `GLINTFX_API` symbol, nothing installed. It exists to explain how glintfx talks to a Wayland compositor today, for whoever extends the platform layer next (a window, a seat, keyboard input): none of these shapes, names, or files are a promise to a consumer, and any of them can change without a version bump. Read [`docs/api-conventions.md`](api-conventions.md) for the one boundary that IS a promise: the error type every fallible call in this project returns, public or not.

## What this covers, and what it does not

`glintfx::platform::wayland_display_adapter` (`src/platform/wayland/display_adapter.hpp`) is the one thing on this platform that owns a live connection to a Wayland compositor. As of this writing it can: connect, discover what the compositor offers, resynchronize on demand, pump incoming events without blocking a caller's own frame loop, and wait for one with a caller-given time budget (`wait_events()`, below) instead of either blocking forever or spinning. It cannot yet bind a seat or read a single keystroke - those are later slices built on top of the same class, not a second competing one.

This document also covers `wayland_egl_context_adapter` (`src/platform/wayland/egl_context_adapter.hpp`), the sibling type that turns an already-open window's own `wl_surface` into a real, current-able OpenGL 3.3 core context ("The EGL context", below). It is a separate class from `wayland_display_adapter` - it does not own the connection, it is handed a surface that already belongs to one - but it lives in the same directory, is built on the same "no protocol type escapes this header" discipline, and is exactly the kind of thing whoever extends this platform layer next needs to understand alongside the display connection itself.

## Opening a connection

`open()` does three things, in order, and only reports success once all three have happened:

1. Connects to the compositor the same way every Wayland client does - reading `WAYLAND_DISPLAY`, falling back to the socket named `wayland-0` inside `XDG_RUNTIME_DIR` when that variable is unset. There is no way to point this at a hand-picked socket name, and none is planned: a consumer that needs that is not this library's target.
2. Asks the compositor for its registry - the object that will announce every capability (interface) the compositor offers.
3. Performs one round trip with the compositor before returning. This is what closes the initial burst of announcements every compositor sends right after the registry is created: by the time `open()` returns successfully, `globals()` (below) already lists everything that was available at connection time.

Any refusal along this path - no compositor listening, the registry request rejected, the round trip itself failing - comes back as an ordinary `glintfx::gltfx_rslt<void>` error (`gltfx_err_code::platform_failure`), never an exception, never a process-ending signal. `open()` also cleans up after itself on failure: nothing is left half-open. `is_open()` tells a caller whether a connection is currently held.

## What the compositor announced: the global catalog

Once open, `globals()` returns a flat catalog of every capability the compositor is currently offering - `wl_compositor`, `xdg_wm_base`, one `wl_output` per monitor, and so on. Each entry carries three things: the numeric name a later bind call would need, the interface name (a string like `"wl_seat"`), and the version the compositor is offering for it - not the version this library understands, the version the *server* announced. The catalog stays current after the initial round trip too: as the compositor adds or removes a capability at runtime (a monitor plugged in, one unplugged), the adapter updates the catalog on its own, with no action required from the caller.

Two ways to read the catalog: look up whether a given interface is present at all (the common case - "does this compositor even offer `xdg_wm_base`"), or look up what was announced under one specific numeric name. A compositor typically offers only one instance of most interfaces but several of others (one `wl_output` per monitor); the catalog does not hide that, it just does not yet offer a convenience for enumerating "every instance of X" - that is future work, once something in this library actually needs it.

**Binding to a global, an obligation on the caller, not on this class:** any future code that binds one of these globals must never ask for a version higher than what the compositor just announced - doing so is a protocol violation the compositor is entitled to kill the connection over. The adapter offers a small helper (`global_catalog::clamp_version`) that keeps a bind request to whichever is smaller, what this build understands or what the server just offered; every future bind call in this project is expected to run through it, not to trust a hand-picked version number.

## Resynchronizing on demand: `roundtrip()`

Beyond the one round trip `open()` performs internally, any later code (a window, a seat) that needs to know "has the compositor definitely processed my last request yet" calls `roundtrip()` directly. It blocks until every event already in flight has been handled - the opposite of the event pump described below, which never blocks.

**A Wayland connection that reports one failed protocol operation is permanently unusable from that point on** - this is not a glintfx rule, it is the documented contract of `wl_display` itself. The adapter honors that literally: the first time any protocol operation on a connection fails, the adapter remembers it (`has_fatal_error()`) and never issues another real protocol call on that connection again. Every subsequent `roundtrip()` (or event-pump call) on a connection in that state returns the same diagnostic immediately, without touching the compositor a second time. This is a separate question from `is_open()`: the connection handle is still owned and still needs to be closed to free it, even once it can no longer be used for anything.

When a failure is fatal, the diagnostic carries what the compositor itself reported: the raw OS-level error code always, and - specifically when the failure was a protocol violation - the name of the interface whose request the compositor rejected, attached as the error's "rejected value" (`docs/api-conventions.md`'s token-vocabulary convention: an interface name like `"wl_compositor"` is itself an identifier, never a sentence).

## Pumping events without blocking: `pump_events()`

`roundtrip()` is for "I need an answer now, and I'm willing to wait." A consumer's own frame loop needs the opposite: "is there anything from the compositor RIGHT NOW, and if not, get back to me immediately." `pump_events()` is that call - safe to invoke every single frame without ever stalling the loop that calls it.

What it does, each time it's called:

1. First works through anything already received but not yet handled.
2. Sends out anything this process still owes the compositor (a request queued but not yet flushed to the socket) - and if the kernel's own send buffer is temporarily full, it waits only for room to write, not for a response; this is the one place `pump_events()` can briefly block, and only until the OS confirms it can accept the next write.
3. Checks, without waiting even a moment, whether the compositor has sent anything new.
4. If yes, reads and processes it; if no, returns immediately with nothing left to do.

This is the exact sequence Wayland's own client library documents as the only safe way to integrate its event delivery into a caller-owned loop - a naive "just poll and dispatch" ordering has more than one way to deadlock the connection, and this method exists specifically so nothing above it has to know that.

## Waiting with a budget: `wait_events()`

`pump_events()` answers "is there anything RIGHT NOW"; a caller that has nothing better to do until something arrives - `gltfx_loop`'s own `step()`, sleeping a hidden window instead of spinning it (`docs/plano-w6b-placa-e-laco.md` fatia 7) - needs a third option, between "never wait" and "wait forever": `wait_events(budget_ms)`. It runs the identical four-step sequence `pump_events()` does, through the same internal `dispatch_ready_events(timeout_ms)` (there is exactly one copy of that sequence in this file, parametrized by the timeout, never two near-identical copies that could drift - the same duplication this project's `tests/wait_points.txt` exists to catch), only handing it the caller's own `budget_ms` instead of a hardcoded zero. It returns `true` the moment something was actually read and dispatched within the budget, `false` if the budget ran out with nothing to show for it, and the same fatal-connection error `roundtrip()`/`pump_events()` already report if the connection cannot be used at all.

**The budget is one total, shared by both directions, never `budget_ms` twice over.** A single deadline is computed once, at the top of `dispatch_ready_events()`, from the caller's `timeout_ms`; the outgoing flush (anything this process still owes the compositor, the same step `pump_events()`'s own header comment names as step 2) and the incoming wait each get whatever is left of that one deadline, in order - a flush that used up part of the budget leaves correspondingly less for the read side to wait on, so a caller asking for "at most 50ms" never ends up blocked for closer to 100. The same distinction that separates `pump_events()` from `wait_events()` at the top of this document also reaches into that shared flush step: a `budget_ms == 0` call (`pump_events()`) treats a kernel send-buffer that is temporarily full as forgivable and moves on, while a real, positive budget (`wait_events()`) treats the identical condition as something worth actually waiting out, because the caller asked to wait.

## What this is not, yet

There is no window here. `wayland_display_adapter` connects, catalogs, resynchronizes, and pumps - it does not create a surface, does not know about `xdg_wm_base` beyond seeing it listed in the catalog, and does not read keyboard or pointer input. Those are later slices (a window, a seat) built as siblings inside the same `src/platform/wayland/` directory, extending this adapter's own responsibilities rather than introducing a second, competing connection type.

## The seat: pointer, keyboard, and touch presence

`wayland_seat_adapter` (`src/platform/wayland/seat_adapter.hpp`/`.cpp`, WL-SEAT) and its Win32 counterpart `win32_seat_adapter` (`src/platform/win32/seat_adapter.hpp`/`.cpp`, WIN-SEAT) both answer the same three questions - does this seat have a pointer, a keyboard, a touch/digitizer surface - into the one shared, mechanism-free value type both feed: `glintfx::platform::seat_capabilities` (`src/platform/input/seat_capabilities.hpp`). Neither mechanism is reachable from the other's header; this section is where the two get compared side by side, and where this fatia's own three declared limitations live (`docs/plano-w6a-janela.md` fatia 13 promised this section in 2025-08's own planning; it was written on 10/09/2026, alongside `WIN-SEAT`'s reopening - see `/var/tmp/glintfx-plan/win-seat.md` for the full research trail this paragraph summarizes).

**The two mechanisms:**

- **Wayland** pushes. `wl_seat.capabilities` is a bitmask *event* the compositor sends on bind and again whenever a device class is gained or lost (`wl_seat_add_listener`) - `wayland_seat_adapter` just writes whatever bitmask arrives straight into `seat_capabilities`, no re-derivation needed.
- **Win32** pulls. There is no equivalent push channel for "which device classes exist" - `win32_seat_adapter` reads the fact by enumerating (`GetRawInputDeviceList()` for pointer/keyboard, `GetSystemMetrics(SM_DIGITIZER)` for touch) and treats any change *notification* only as a trigger to re-enumerate from scratch, never as a delta to apply in place. The notification itself, as of 09/09/2026 (`WIN-SEAT` SF-1, `D-090918` in `DECISOES_AUTONOMAS.md`), is `RegisterDeviceNotificationW` on the seat's own message-only window, filtered to `DBT_DEVTYP_DEVICEINTERFACE` for the keyboard and mouse device-interface class GUIDs - **not** `RegisterRawInputDevices`/`RIDEV_DEVNOTIFY`, which Microsoft's own documentation says a library must not use (it is a per-process registration, one window per device class, and interferes with any raw input a consumer registers on its own). `learn.microsoft.com/windows/win32/api/winuser/nf-winuser-registerrawinputdevices`, Remarks, is the exact citation; `src/platform/win32/seat_adapter.hpp`'s own header comment carries the rest of the research trail (SDL3 read for the technique, never copied - GODS_LAWS.md L-29).

**The shared counter.** Both sides expose `last_change()`, a plain monotonic counter that never resets on `close()` - but the two count different *grandezas*, deliberately, and are never compared by equality (`tests/measured_exceptions.txt`'s own `seat_test.capability_events` entry, `lado="ambos"`): Wayland counts `wl_seat.capabilities`/`wl_seat.name` *events*, one per announcement burst (typically 2 on bind: capabilities, then name); Win32 counts *system announcements this adapter reacted to* - 1 for the initial synchronous read inside `open()`, +1 for every routed `WM_DEVICECHANGE`. Only the name and the "at least one announcement happened" shape are shared; the value itself is a fact of mechanism, not a promise of parity.

**Keyboard parity, one rule applied on both sides (`D-WS-5`).** A receiver/dongle that exposes a handful of media keys enumerates as a keyboard-class device on Windows (`RIM_TYPEKEYBOARD`) while the identical hardware never satisfies Linux's own keyboard classification - `systemd`/`udev`'s `ID_INPUT_KEYBOARD` rule (`src/udev/udev-builtin-input_id.c`) requires the first 32 bits of the device's key bitmask to cover Esc, the number row, and Q-through-D before libinput (and therefore the compositor, and therefore `wl_seat`) ever announces `WL_SEAT_CAPABILITY_KEYBOARD` for it. Since 09/09/2026 (`WIN-SEAT` SF-3), `win32_seat_adapter::translate()` applies the same 32-key floor: a `RIM_TYPEKEYBOARD` entry counts as a keyboard only when `GetRawInputDeviceInfoW(RIDI_DEVICEINFO)` reports **zero** keys (unknown - "do not invent absence") or **at least 32**; fewer than 32 excludes it. This is a genuine, deliberate change in observable behavior on real hardware, marked `⚠` for the leader's ratification in `DECISOES_AUTONOMAS.md` (D-WS-5) - not something either mechanism silently decided on its own.

**Three limitations, declared rather than silently absent:**

1. **Remote Desktop is blind on Windows, and Wayland has no equivalent case.** `GetRawInputDeviceList`'s own documentation states plainly: "Input devices accessed through Remote Desktop Protocol (RDP) do not appear in the raw input device list." A user connected over RDP therefore reads `pointer=0 keyboard=0` from this adapter while actively typing. Not fixed by this fatia - tracked as its own open item (`SEAT-RDP-BLIND` in the project's pendency inbox), because either answer (assume presence, or report the honest absence) is itself an invented guess Wayland's own mechanism never has to make, and the choice belongs to the leader, not to an agent.
2. **Touch hotplug is not proven live on Windows, by Microsoft's own admission.** `GetSystemMetrics(SM_DIGITIZER)` is re-read every time this adapter recomputes capabilities, but Microsoft's own multi-touch documentation names the limitation directly: "there are some inherent limitations for `SM_GETSYSTEMMETRICS`... there is no support for plug and play." A digitizer attached mid-session may only be reflected the next time something else (a keyboard/mouse notification) triggers a re-read, or not at all until the next `open()`.
3. **Real device connect/disconnect is not exercised by any CI environment on either side.** The `windows-latest` runner and the container's own `kwin_wayland --virtual` compositor both lack a real, pluggable keyboard/mouse - `seat_test`/`two_seats_test` on both platforms prove the *routing* (a synthetic `WM_DEVICECHANGE`, or the container's own bind-time `wl_seat.capabilities`), never a live hardware event delivered end to end. The only environment that can prove that is the optional Windows lab (`tools/win-vm-lab/`, `virsh attach-device` of a virtual USB mouse) - never the leader's own live session (GODS_LAWS.md L-09/L-50) - and it is not a closure criterion for either fatia.

## The EGL context: turning a surface into something OpenGL can draw to

`wayland_egl_context_adapter` (`src/platform/wayland/egl_context_adapter.hpp`/`.cpp`, `docs/plano-w6b-placa-e-laco.md` fatia 3) is what `glintfx::gltfx_gl_context::open()` (the public, cross-platform handle - see `docs/gl-loop-portability-matrix.md`) resolves to on this platform. It never owns a `wayland_display_adapter` reference of its own: it is handed an already-open window's own `wl_surface`, and reaches the `wl_display` that surface already belongs to through that surface (`wl_proxy_get_display()`), the same way `create_egl_display()` below needs no separate connection object passed in.

**Opening one, in order, each step named for what it actually asks the system for:**

1. `create_egl_display()` - `eglGetPlatformDisplay(EGL_PLATFORM_WAYLAND_KHR, ...)` over that `wl_display`, then `eglInitialize()` and `eglBindAPI(EGL_OPENGL_API)` (the latter is a per-thread setting in EGL, and has to run before the next step).
2. `choose_config()` - reads the `msaa_samples`/`srgb_framebuffer` options (`open_only`, already fixed for this window by the time this adapter is ever asked, D-W6b-25) and asks EGL for a matching `EGLConfig`; a driver that cannot offer what was asked for makes this option answer `unsupported_here` rather than silently handing back a lesser config (D-W6b-17 - this project never degrades a graphics option in silence).
3. `create_egl_window()` - `wl_egl_window_create()` over the surface, sized in **pixels** (the window's own `pixel_size()`, never `logical_size()` - a HiDPI screen makes those two numbers different, and this is the same distinction `docs/window-portability-matrix.md` documents for the window itself).
4. `create_context()` - `eglCreateContext()` requesting the 3.3-core profile this project's public API promises everywhere (`gl_version_policy.hpp`, one directory up in `src/platform/gl/`, is what actually judges whatever the driver hands back), then `make_current()`, then `eglSwapInterval(m_egl_display, 0)` - **always 0, never 1**, for a reason the next paragraph explains.

**Why `eglSwapInterval` is never 1, and what replaces it:** at interval 1, `eglSwapBuffers()` itself installs the compositor's `wl_surface.frame` callback and blocks inside the call until that callback fires - which is exactly what a surface the compositor is not currently repainting (another workspace, minimized, screen off) may never do, hanging the entire calling thread, not just rendering (this fatia's own research, `docs/plano-w6b-placa-e-laco.md` sec. 0, cites the upstream bug reports this exact failure mode produces in other projects). Interval 0 makes the driver never install that callback on its own, which is what lets this project manage the SAME callback itself, on its own terms, through `frame_callback_sequence.hpp` - a pure atom, with no EGL or Wayland type reachable from its header, that turns "is a callback from the previous frame still outstanding" plus a caller-supplied time budget into one of three plans (present immediately, poll for the remainder of the budget then decide, or give up without polling at all when the budget is already zero) - the SAME "budget is read, never presumed" discipline `wait_events()` above documents for event pumping, applied here to presentation instead. `swap_buffers()` drives that atom, actually calls `eglSwapBuffers()` when the plan says to, and reports back one of exactly two outcomes: `presented`, or `skipped_hidden` when the budget ran out with the previous frame's callback still unacknowledged - never a third, silent option. `close()` tears the four steps above down in the reverse order they were built, the same convention `wayland_display_adapter::close()`'s own destructor-adjacent cleanup already uses.

## Where to look for the code itself

`src/platform/wayland/display_adapter.hpp`/`.cpp` (the adapter, its four connection operations, and `wait_events()`) and `src/platform/wayland/global_catalog.hpp`/`.cpp` (the catalog, deliberately free of any Wayland header - it is a plain record type, testable without a compositor at all). For the EGL context: `src/platform/wayland/egl_context_adapter.hpp`/`.cpp`, and `src/platform/wayland/frame_callback_sequence.hpp`/`.cpp` for the pure atom that decides when a frame presents versus skips. For the seat: `src/platform/input/seat_capabilities.hpp`/`.cpp` (the shared value type), `src/platform/wayland/seat_adapter.hpp`/`.cpp`, and on Windows `src/platform/win32/seat_adapter.hpp`/`.cpp` plus its two pure atoms `src/platform/win32/device_change_message.hpp`/`.cpp` (classifies a `WM_DEVICECHANGE` message) and `src/platform/win32/raw_device_facts.hpp` (the keyboard-key-count fact `translate()` needs for the 32-key parity rule). All of these files carry extensive comments on the exact sequencing and the specific pitfalls each step avoids; this document explains the shape and the why, the source is where the line-by-line mechanics live.
